# 校园智慧水务系统架构与业务对象

本文描述一个典型校园水务平台的业务分层，用于 RAG 演示和系统设计讨论。实际学校的设备型号、网络拓扑、数据保留周期和权限规则必须以现场资料为准。

## 1. 业务域

校园水务通常包含以下业务域：

1. **计量域**：水表、分区计量、总表、累计量、瞬时流量和计量校准。
2. **水质域**：pH、浊度、余氯、电导率、溶解氧等监测点和人工采样。
3. **设备域**：设备档案、编码、在线状态、电池、固件、网关和维护记录。
4. **告警域**：阈值告警、趋势告警、离线告警、数据质量告警和告警闭环。
5. **工单域**：巡检、报修、派单、处理、验收、关闭和复盘。
6. **分析域**：日/月用水统计、分区对标、漏损分析、节水项目评估和预测。

## 2. 数据流

```text
水表/水质传感器
    → 边缘网关
    → 消息接入与协议解析
    → 实时缓存 / 时序数据库
    → 规则计算与告警
    → 看板、报表、Agent 工具
```

原始报文应尽量保留，解析后的标准数据应带有设备编码、采集时间、服务端接收时间、单位、质量标记和来源。原始时间与接收时间不同步时，分析应明确采用哪个时间。

## 3. 常见服务边界

- **设备接入服务**负责通信、协议解析和设备心跳，不负责生成业务结论。
- **IoT 数据服务**负责查询设备、分区和校区的实时或历史数据。
- **告警服务**负责规则计算、通知、确认和状态流转。
- **维修服务**负责工单和报修状态，不应由只读查询接口直接写入。
- **预测服务**负责模型调用、缓存、知识问答和回答编排。
- **知识库服务**负责静态资料摄取、切分、检索和来源返回。

服务之间传递的数据要有稳定的契约。接口名称相同但单位、时间范围或空值语义不同，会导致 Agent 生成看似合理但实际错误的回答。

## 4. 核心业务对象

### 设备 Device

至少包含设备编码、设备类型、校区、建筑、楼层、单元、安装位置、网关、在线状态、最近上报时间和维护状态。

### 测点 Measurement Point

一个设备可以提供多个测点，例如瞬时流量、累计流量、电池电压和信号强度。测点应明确数据类型、单位、采样周期、精度和质量标记。

### 时间序列 Sample

建议字段包括 `deviceId`、`metric`、`value`、`unit`、`eventTime`、`ingestTime`、`quality` 和 `traceId`。同一个时间点重复上报时应有去重策略。

### 告警 Alert

告警记录应保留规则版本、触发值、基线值、严重程度、开始时间、结束时间、确认人和关联工单。告警状态不能只用一个布尔字段表达。

### 工单 Work Order

工单至少包含来源告警、设备或区域、描述、优先级、处理人、处理过程、附件、结果、验收人和关闭时间。Agent 生成工单时应先形成草稿并等待确认。

## 5. 实时数据与知识数据的边界

“这台设备现在是否在线”“今天用了多少水”属于实时业务问题，应调用业务接口；“水表离线如何排查”“SWMM 的子汇水区是什么”属于静态知识问题，可检索文档。混合问题应先调用实时工具，再用知识库解释结果。

## 6. 可靠性注意事项

- 设备离线时不要把最后一条数据标成当前数据。
- 累计量必须确认重置、换表和溢出事件。
- 统计口径要区分自然日、计费日、时区和采集时间。
- 发生数据延迟时要展示数据时间，而不是只展示查询时间。
- 公共安全相关信息要给出数据新鲜度和人工复核要求。
